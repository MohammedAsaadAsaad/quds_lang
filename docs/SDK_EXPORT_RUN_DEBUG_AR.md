# إصلاح تشغيل تحويل Fraction عبر إعادة تصدير SDK — 2026-11-17

## بلاغ المستخدم

```quds
# src/some.quds
use quds:math
export quds:math

augment int:
  explicit cast (value: int) -> Fraction:
    return Fraction(value, 1)
```

```quds
# main.quds
use src.some

main():
  print "test_lang_quds"
  f: Fraction = 1
  print f
```

أُعيد إنتاج الرسالتين: some.dart غير موجود في مجلد الخرج، ثم quds_math.dart
غير موجود أيضًا. تشغيل build أولًا كان يصلح الملف الأول فقط؛ لم يكن يحل
التبعية غير المباشرة إلى SDK. لم تكن المشكلة في use/export أو المسافة قبل
قوس cast أو المعاملات الموضعية لمنشئ Fraction؛ هذه الصيغ مقبولة.

## السبب والإصلاح

- مسار run كان يضمن الملف الرئيسي فقط، ومسار التصحيح كان يولّده دون تجهيز
  شجرة تبعياته. صار التشغيل يضمن المخرجات التابعة حتى مع وجود كاش صالح للرئيسي،
  ويستعمل التصحيح بناء الشجرة كاملة قبل بدء VM. مسار إخراج Flutter الموجود
  يستعمل تجهيز الشجرة نفسه دون إضافة صياغة خاصة إلى اللغة.
- جمع حزم SDK كان يعتمد على الاستيرادات المباشرة. صار يضم مكتبات SDK التي
  استُخدمت عبر إعادة التصدير والتحويلات أيضًا.
- توضع حزم SDK وruntime المشترك في مجلد موحد داخل خرج المشروع، وتوجّه
  import/export المولدة إليه من المجلدات الفرعية. هذا يحفظ هوية Fraction
  وConversionError بين الملف الرئيسي والملفات التابعة، بدل إنشاء نسخ Dart
  مختلفة من النوع نفسه في كل مجلد.
- يسجل الكاش بصمات ملفات الحزم وخرائط المصدر؛ يُصلح التشغيل ملفات الخرج
  المحذوفة أو التالفة، ويعيد التحقق من ملف رئيسي مخزن بعد بناء تبعية قد تغيّر
  حزمة SDK المشتركة. لا يُستدعى اسم مساعد من حزمة أقدم مع حزمة أعيد توليدها.
- أخطاء أجسام التبعيات توقف التشغيل بتشخيص .quds قبل دخول main، ولا تُترك
  لاكتشافها عبر رسائل Dart عن ملفات أو أسماء مفقودة.

## هل explicit مطلوب في هذا المثال؟

لا. explicit لا يشارك في إسناد `f: Fraction = 1`. الإسناد هنا يستعمل أصلًا
التحويل الضمني الموجود داخل Fraction في lib/sdk/math.quds. لذلك يمكن تبسيط
some إلى إعادة التصدير فقط:

```quds
# src/some.quds
export quds:math
```

```quds
# main.quds
use src.some

main():
  f: Fraction = 1
  g = 1 to Fraction
  print "{f.numerator}/{f.denominator}"
  print g.numerator
```

اختُبر هذا المثال عبر run؛ الناتج `1/1` ثم `1`. أما `print f` في المثال الأصلي
فيطبع حاليًا `Instance of 'Fraction'`؛ لم يضف هذا الإصلاح صيغة toString جديدة.

إذا عرّفت تحويلًا explicit لنوع لا يملك التحويل نفسه، تستعمله بـ `value to Type`
أو `value to? Type`. لكن التعريف الإضافي int → Fraction يكرر هنا تحويل SDK
القابل للاستدعاء صراحة أيضًا؛ إبقاء التعريفين ثم كتابة `1 to Fraction` يؤدي
إلى E310 للغموض وفق القاعدة المعتمدة، ولا يُحسم بالتغلب حسب ترتيب الاستيراد.
تحويل تعريفك إلى implicit لا يحل التكرار؛ يصبح الإسناد نفسه غامضًا.

`use quds:math` يلزم إذا استعمل جسم some أسماء SDK محليًا، بينما `export`
يتيحها للمستورد. مع إعادة التصدير وحدها لا تحتاج use إضافية داخل some.

## إعادة الفحص

```sh
dart run bin/quds.dart test test/export_cast.quds
dart test test/export_cast_test.dart --reporter expanded
dart format --output=none --set-exit-if-changed .
dart analyze
dart test --reporter expanded
```

الاختبارات تشمل تجربة قدس، وتشغيل مشروع جديد دون build مسبق، وتحليل Dart
المولد، وهوية SDK والاستثناءات بين مجلدين، وحذف/إتلاف المخرجات ثم إعادة التشغيل،
وحالة كاش أقدم ذات أسماء مساعدين مختلفة، ورفض جسم تابع غير صالح، وlaunch
فعليًا عبر DAP مع التوقف على سطر قدس 5. fixtures تحت test/fixtures/export_cast.

حدّث نسخة Quds المنفذة وأعد تشغيل المصحح. لا يحتاج المثال إلى إنشاء ملفات
Dart يدويًا أو حذف الكاش؛ المسار المعدل يتحقق منه ويصلح المخرجات الناقصة.
النتائج الدقيقة في [VALIDATION.md](VALIDATION.md). لم تتغير صياغة اللغة أو قواعد
التحويلات لحل خطأ بناء الملفات.
