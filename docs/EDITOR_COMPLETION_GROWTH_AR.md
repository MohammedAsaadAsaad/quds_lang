# إصلاح تدهور الإكمال مع نمو الملف — 2026-11-17

بلاغ المستخدم: الإكمال الأول سريع، ثم يصبح شديد البطء أو لا تظهر الاقتراحات
عند زيادة الملف. أُعيد إنتاج عيوب مستقلة؛ هذا إصلاح للمحرر لا تعديل لصياغة اللغة.

## الأسباب والإصلاحات

1. **التلوين يحجب الإكمال:** كان semanticTokenData يحوّل إزاحات UTF-8 إلى
   مواقع UTF-16 بإعادة قراءة الملف من بدايته لكل رمز، ثم يعيد حساب النتائج في
   كل طلب تلوين على isolate استقبال الطلبات. أضيف SourceIndex بمرور واحد
   وفهارس للسطور والبايتات، مع اختبار العربية وemoji وCRLF. يعمل حساب التلوين
   في العامل الخلفي، ويعيد الخادم البيانات المخزنة نفسها لنسخة النص الحالية.
2. **البحث عن نوع المستقبل:** كان إكمال الأعضاء يمسح AST كله ويعيد تحويل
   إزاحات كل تعبير ونسخ النص بينه وبين المؤشر، حتى حين يكون المتغير معروف النوع.
   يُستخدم رمز النطاق المعروف مباشرة؛ وعند الحاجة إلى AST تُرفض التعبيرات
   البعيدة قبل تحويل الإزاحات أو فحص الفجوة. يبقى دعم الاستدعاءات والأقواس والسلاسل.
3. **سطر غير مكتمل يلغي السياق الجديد:** يحاول العامل الخلفي إزالة العضو غير
   المكتمل بعد النقطة مع حفظ المستقبل، ثم عزل السطر الجاري عند الحاجة. يُحلل
   النص المستعاد لاستخراج الرموز الجديدة، وتبقى التشخيصات للنص الحقيقي. لا تُقبل
   رموز التحليل السابق إذا تغيّر السياق السابق للمؤشر. لا يجري طلب الإكمال
   ترجمة متزامنة أو قراءة ثقيلة كحل بديل.
4. **أسماء تنتهي بأرقام:** كانت values2. تُعامل كأنها العدد العشري غير المكتمل
   2.، فلا يدخل الطلب مسار إكمال الأعضاء. أصبح التمييز يعتمد بداية اسم المستقبل.
5. **العامل والطلبات:** يشمل احتواء الأخطاء مراحل الاستعادة والتشخيص أيضًا،
   وتُعاد تهيئة العامل إن توقف، دون ترك الطابور busy إلى الأبد. طلبات الإضافة
   لها إلغاء وتنظيف ومهلة انتهاء؛ تُهمل الردود القديمة والنتائج التي تخص نسخة
   سابقة من المستند. تعيد الإضافة طلب التلوين عند وصول تشخيصات النسخة الحالية.

## قياسات فعلية وحدودها

البيانات الخام: [editor_growth.json](../bench/results/editor_growth.json).

| عبء العمل | قبل إصلاح الفهرس | بعده |
| --- | ---: | ---: |
| حساب التلوين لـ100 ربط | 8.744ms | 6.306ms |
| حساب التلوين لـ1,000 ربط | 177.613ms | 16.778ms |
| حساب التلوين لـ5,000 ربط، نحو 10 آلاف سطر | 4626.412ms | 68.124ms |

هذه عينات مرتبة حسب الحجم في عملية Dart، وليست حدودًا مضمونة. الاختبار السابق
ذو الملف الصغير في EDITOR_PERFORMANCE_DEBUG_AR.md لم يكن يغطي تدهور الحجم.

قياس stdio الفعلي بعد الإصلاح، على الملف الكبير نفسه، يرسل طلب تلوين ثم طلب
إكمال، ويشمل framing وJSON decoding ونقل النتائج عبر pipe:

- عشر عينات؛ الوسيط **75.374ms**، وp95 **178.727ms**.
- آخر تعديل غير مكتمل، ثم انتظار تحليله الخلفي وإكماله: **387.655ms**.
- هذا الطلب العام يعيد آلاف الأسماء، وليس إكمال عضو بقائمة صغيرة.
- لا يشمل القياس رسم واجهة VS Code أو تهيئة عملية الخادم. لا ندّعي قياسًا
  مرئيًا على جهاز المستخدم أو ضمان زمن موحد لكل أنواع مشاريع Dart/Flutter.

## إعادة الاختبارات

```sh
dart run tool/profile_editor_growth.dart
node test/editor/lsp_growth.cjs dart
dart test test/editor_test.dart test/editor_growth_test.dart --reporter expanded
node --check editors/vscode/extension.js
dart format --output=none --set-exit-if-changed .
dart analyze
dart test --reporter expanded
```

الاختبارات تغطي نمو مستند على ثلاث دفعات غير مكتملة، ظهور المتغيرات الجديدة
مع استمرار التشخيص الحقيقي، إعادة استعمال بيانات تلوين ملف 5,000 ربط، وعدم
تعطل ملفات أخرى بعد فشل تحليل تعبير عميق. يوجد اختبار اتصال LSP حقيقي، واختبار
للإضافة يحاكي VS Code لفحص الإلغاء والمهلة والرد المتأخر وتحديث التلوين.
فحص الاتصال له حد واسع قدره 3 ثوانٍ لاكتشاف حجب طلبات الخادم، وليس ادعاءً بأن
هذا زمن الإكمال المطلوب أو المعتاد.

## تفعيل الإصلاح عند المستخدم

حدّث نسخة Quds، وحدّث الإضافة المثبتة أيضًا عبر `quds install` أو تثبيتها من
`editors/vscode`، ثم نفّذ **Developer: Reload Window**. إعادة تشغيل الخادم وحدها
لا تحمّل JavaScript الجديد لإضافة مثبتة بنسخة قديمة. بعد ذلك يمكن استعمال
**Quds: Restart Language Server**. إذا بقيت المشكلة، يفيد ملف مصغر يعيد إنتاجها
ومخرجات قناة Quds لتحديد حالة إضافية، دون افتراض أن الخلل من جهاز المستخدم.

سجل التحقق النهائي في [VALIDATION.md](VALIDATION.md).
