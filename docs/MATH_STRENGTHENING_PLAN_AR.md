# خطة تعزيز مكتبة الرياضيات في Quds

تاريخ الخطة: 2026-11-15.
خط الأساس: `bf8fbf2` على `main`، بعد إصلاحات المراجعة العددية.
هذه **خطة عمل مقترحة** وليست إعلانًا عن تنفيذ المراحل التالية.

## الهدف

تحويل `quds:math` من مكتبة واسعة ذات اختبارات أمثلة إلى مكتبة ذات عقود عددية
واضحة، ومجالات مدعومة، واختبارات مستقلة، وأداء مقاس، وإصدارات يمكن الاعتماد عليها.
الأولوية لصحة الموجود واستقراره قبل زيادة عدد الدوال.

لا نعد بدقة موحدة لجميع الدوال أو كل المدخلات. المطلوب أن يعرف المستخدم لكل
عملية: المجال المدعوم، والدقة المتوقعة، وشروط الخوارزمية، وكيف يظهر الفشل.

## ما لدينا الآن

- 292 دالة عامة عليا، و20 صنف قيمة عامًا، وثلاث مجموعات extensions.
- 2591 حالة مرجعية أو هوية عددية مجمدة، مع مراجع من NumPy وSciPy وmpmath.
- مجموعة Quds الحالية، وعشر حالات انحدار كانت تفشل وأصبحت تمر.
- فحص استيراد وتشغيل للمكتبة المولدة على JavaScript عبر Node.
- إصلاحات overflow والحساب المعياري والاحتمالات ودوال خاصة والجبر الخطي
  والتقارب، مع تطابق المصدر ونسخته المضمنة.
- نتائج التحقق والحدود في [MATH_ACCURACY.md](MATH_ACCURACY.md)، والتتبع في
  [MATH_COVERAGE.md](MATH_COVERAGE.md)، والنتائج العامة في [VALIDATION.md](VALIDATION.md).

وجود استدعاء اختباري لكل دالة ليس تغطية لجميع فروعها. والنجاح على شبكة مدخلات
لا يثبت حد خطأ عالميًا؛ هذه فجوتان أساسيتان تعالجهما الخطة.

## الضوابط

1. اقرأ `AGENTS.md` ومواصفة Quds 1.2 قبل تغيير المترجم أو صياغة الأمثلة.
2. لا تغيّر لغة Quds أو API قائمًا بصمت لتسهيل خوارزمية عددية. وثّق أي تغيير
   في الدلالة أو المجال أو الأخطاء، وأرفق قرار توافق وترحيل عند الحاجة.
3. حافظ على تقييم التعبيرات مرة واحدة ومن اليسار إلى اليمين، وعلى دلالات
   مراجع Dart. ربط final لا يعني تجميد الكائن أو وجوب نسخه عميقًا.
4. اختبر Quds الحقيقي والمخرجات الناتجة منه؛ لا تجعل التنفيذ محل الاختبار
   هو نفسه مولّد الإجابات المتوقعة، ولا تعتمد على تعديل Dart المولد يدويًا.
5. لا تجعل `NaN` أو صفرًا أو آخر iterate بديلًا صامتًا لفشل التقارب.
6. لا توسّع tolerances أو تغيّر التوقعات لمجرد جعل الاختبار أخضر. اربط أي
   سماحية جديدة بتحليل خطأ أو مرجع أو استقرار إحصائي موثق.
7. استخدم checkout الموجود واحفظ تغييرات المستخدم. لا تنشئ worktree أو تنشر
   حزمة أو تغيّر البيئة المنشورة دون طلب مناسب.

## المرحلة 0 — تثبيت خط الأساس

### العمل

- اسحب أحدث `main` بعد فحص حالة Git وحفظ العمل المحلي.
- سجّل SHA وإصدارات Dart وNode والنظام ومراجع Python المستعملة للتوليد.
- شغّل الفحوص الحالية دون تعديل التوقعات أو تحديث الاعتماديات صامتًا.
- تحقق من تطابق `lib/sdk/math.quds` و`mathSdkSource`، ومن أن إعادة توليد
  المرجع لا تغيّر البايتات على بيئة التوليد المحددة.
- افصل نجاح الترجمة عن نجاح التنفيذ وعن رفض المدخلات المتوقع، وأظهر التخطي.
- احتفظ بالأرقام والهوية والنسخة المرجعية لكل إخفاق؛ لا تعتمد على لقطة stdout
  دون تأكيد أن الحالات المقصودة نُفذت.

### القبول

- نتائج كاملة وأسباب أي إخفاق أو تخطٍّ، مع صفر إخفاق عددي غير مفسر قبل التطوير.
- لا يتغير المصدر أو lockfile بسبب خطوات الإعداد وحدها.
- يُشخّص اختبار debug المتذبذب منفصلًا؛ لا يُسمح له بإخفاء إخفاقات الرياضيات.

## المرحلة 1 — عقد عددي لكل دالة ونوع

أنشئ سجلًا منظمًا قابلًا للمعالجة، مع وثائق بشرية مولدة منه. لا تستخدم جدول
وجود الاستدعاءات الحالي بوصفه بديلًا عن هذا السجل.

### حقول السجل

- الاسم والتوقيع والمعنى الرياضي والوحدات واتفاقية الترتيب/الفهرسة.
- مجال كل وسيط، والعلاقات بين الوسائط، وحدود العمل والذاكرة.
- السلوك عند الحدود، والقوائم الفارغة، وNaN و±Infinity و±0 حيث ينطبق.
- شروط مثل التناظر، والإيجابية المحددة، وكون المصفوفة قابلة للعكس، واستقلال
  الأعمدة، ونعومة الدالة أو أحادية قمة دالة التحسين.
- نوع الدقة: exact integer، أو خطأ مطلق/نسبي، أو ULP، أو خطأ إحصائي، أو باقٍ
  أو تقدير خطأ تقريبي. اذكر أثر عدد الشرط بدل وعد موحد بعدد من الخانات.
- سلوك الفشل: مجال غير صالح، overflow، عدم تقارب، مدخل غير قابل للتمييز عدديًا.
- التعديل والـaliasing: هل يُعدَّل المدخل؟ هل الناتج نسخة؟ هل مصفوفات النتائج
  قابلة للتعديل؟ لا تُدخل deep copy أو readonly على جميع النتائج بلا قرار.
- المرجع المستقل والاختبارات والمنصات ودرجة النضج.

### قرارات تحتاج مراجعة API

- هل تبقى الاستثناءات النصية، أم تُستبدل بأنواع أخطاء موحدة؟ اختر عقدًا مع
  ترحيل واضح؛ يجب أن تختبر حالات الرفض نوع/سبب الخطأ لا مجرد وقوع أي استثناء.
- توحيد حدود الاحتمال 0 و1: بعض quantiles الحالية تقبل المجال المفتوح فقط.
  لا تغيّر ذلك دون توثيق؛ قد يكون infinity نتيجة صحيحة في API آخر.
- توضيح الفرق بين `logGamma` بمعنى log(abs(Gamma)) وبين logarithm مركب.
- حماية invariants للأنواع مثل `Fraction`: الفرق بين المصنع الذي يطبّع
  القيم والمنشئ الخام. لا تدّعِ أن كل constructor يضمن الاختزال إن لم يتحقق منه.
- توصيف `kendall` الذي يستبعد الأزواج المتعادلة مقابل `kendallB`، وعدم تسويق
  مقدّر مختلف تحت اسم إحصائي ملتبس.

### القبول

سجل لكل الدوال الـ292، ولكل نوع وextension عام، دون خانة دقة أو فشل مبهمة.
صنّف الميزات إلى تجريبية أو مختبرة على مجال محدد أو مستقرة وفق أدلة مكتوبة؛ لا
تستنتج الاستقرار من عدد الاختبارات وحده.

## المرحلة 2 — منظومة التحقق

### مراجع مستقلة

- احتفظ بالـfixture المجمدة لتشغيل CI دون Python.
- ثبّت بيئة توليد منفصلة وإصدارات المراجع وسجل مصدر كل قيمة ودرجة دقتها.
- استخدم mpmath بدقة 80–200 خانة لنقاط الحدود والذيول، وارفع الدقة للتحقق
  من استقرار الإجابة؛ لا تفترض صحة SciPy عندما تدخل قيمتها في underflow.
- اختلف بالمناهج عند الإمكان: مرجع مستقل + هوية تحليلية + باقي، بدل مقارنة
  تنفيذين مشتقين من الصيغة غير المستقرة نفسها.

### توليد المدخلات

- شبكات لوغاريتمية للمقادير الصغيرة والكبيرة والقيم حول الصفر وحدود المجال.
- نقاط حول حدود الانتقال بين خوارزميتين، وحول poles ونقاط تفرع الدوال الخاصة.
- خصائص بأرقام عشوائية وبذور ثابتة، ثم corpus أكبر في تشغيل دوري، مع تقليل
  المدخل الفاشل وحفظه regression دائمًا.
- فئات مصفوفات: صفرية، قطرية، متعامدة، ناقصة الرتبة، شبه مفردة، غير متناظرة،
  ذات مقاييس مختلفة، وقيم ذاتية مكررة أو تقارب بينها.
- مدخلات غير صالحة تتحقق من **الخطأ المقصود**، لا من نجاح wrapper يلتقط أي خطأ.

### معايير الدقة

- القيم الصحيحة تقارن exact بمراجع arbitrary precision، دون تحويلها إلى double.
- قرب الصفر يلزم حد مطلق مناسب أو فحص نسبي صريح؛ لا تجعل absolute tolerance
  الكبير يسمح بعودة صفر بدل احتمال صغير مطلوب.
- افحص النتائج بعد تطبيع المقاييس، واستخدم ULP عندما يكون مناسبًا لدالة scalar.
- اختبر الاستمرارية/الاتساق حول حدود الخوارزميات، والـmonotonicity عندما تكون
  خاصية رياضية مثبتة، لا لمجرد توقع بصري.
- جرّب mutation testing منتقى: إفساد sign أو شرط حد أو عامل في kernel يجب أن
  يفشل اختبارات مرتبطة به. هذه وسيلة لتقييم قوة الفحوص وليست مقياسًا وحيدًا.

### القبول

وجود فئات حدود ورفض وخصائص لكل API بحسب عقده، وفشل الاختبارات عند إعادة
إدخال العيوب العشر القديمة. يذكر كل ملخص عدد الحالات المنفذة والإخفاقات
والتخطيات؛ لا يُقبل تشغيل صفري أو توليد مراجع من التنفيذ محل الاختبار.

## المرحلة 3 — الأعداد الصحيحة والاحتمالات والإحصاء

### الأعداد الصحيحة والكسور

- وسّع اختبارات قرب حدود 64-bit و53-bit، والإشارات، وصفر/واحد، وقيم minimum.
- قارن modular multiply/power/inverse وCRT وBezout بمراجع BigInt مستقلة، بما
  يشمل moduli غير أولية وأنظمة متكررة ومتوافقة وغير متوافقة.
- اختبر الأولية باستخدام قائمة primes/composites موثوقة وCarmichael numbers
  وstrong pseudoprimes مع توثيق مجال قواعد Miller–Rabin.
- تحقق من factorization عبر حاصل العوامل بمقدار غير محدود، وأولية العوامل
  وترتيبها، واختبر budgets وخروج Pollard عند فشل التقسيم.
- للكسور: canonicalization والإشارات والعمليات المتقاطعة والاختزال المبكر
  والإلغاء إلى الصفر، ومنع نتيجة صحيحة شكلًا بسبب التفاف numerator وdenominator.
- افصل خيار API غير محدود الدقة، إن احتجناه، عن API `int` الحالي. تحقق أولًا
  من دعم BigInt في interop والمترجم؛ لا تفترض أن جميع معاملاته متاحة في Quds.

### التوزيعات

- أضف جداول log-PMF وlog-PDF وsurvival/log-survival قبل حسابات الذيول الشديدة
  إذا أثبتت الحاجة إليها؛ لا تغيّر دلالات CDF الحالي إلى survival.
- اختبر مجموع PMF، وعدم السلبية، وحدود CDF ورتابتها، وعلاقة PDF/CDF حيث تصلح،
  والعكس بين CDF والـquantile مع سماحية تراعي عدد الشرط في الذيل.
- اختبر cancellation عند `1 - cdf`؛ توفير SF مباشرة أفضل من ادعاء دقة ذيل
  صغير لا يمكن استرجاعه بعد تقريب CDF إلى 1.
- راجع تصحيح ties وcontinuity ودرجات الحرية والافتراضات في اختبارات الفرضيات.
  ميّز exact عن asymptotic وعن الفرضيات مثل تساوي التباين.

### أخذ العينات

- تحقق من المتوسط والتباين والـquantiles بأحجام وبذور متعددة، وعرّف مستوى الخطأ
  الإحصائي واحتمال إنذار زائف قبل استعمال الاختبار بوصفه بوابة إصدار.
- افحص الانحياز حول تبديل خوارزمية Poisson، والمعلمات الصغيرة لـgamma/beta.
- افصل اختبار RNG عن sampler، واختبر نفاد ميزانية rejection ومصدر عشوائي
  يعيد قيم الحدود دون تعليق العملية.

### القبول

لا overflow صامت ضمن المجال المعلن، واتفاق المراجع في شبكة الحدود المحددة،
وتوثيق أي نتيجة تقريبية أو أي رفض بسبب حدود التمثيل والعمل.

## المرحلة 4 — الجبر الخطي والهندسة

- اختبر LU/QR/Cholesky/SVD باستخدام بواقي مطبعة وعلاقات إعادة البناء.
- للـSVD: orthogonality للجانبين، وترتيب وعدم سلبية singular values، وحالات
  الصفر ونقص الرتبة والأبعاد المستطيلة، وأثر العتبة على pseudoinverse.
- تحقق من هويات Moore–Penrose الأربع، لا من بعض عناصر معكوس بسيط فقط.
- اختبر القيم والمتجهات الذاتية عبر `A v - lambda v`، وأيضًا subspaces عند
  التكرار؛ مقارنة متجه بعينه ليست صحيحة بسبب حرية الإشارة والطور.
- قارن least squares بالباقي وحلول minimum norm، واختبر matrices سيئة التكييف
  مع حدود forward/backward error مناسبة، وأظهر rank المستخدم في الحل عند الحاجة.
- للـmatrix exp/log/sqrt: تحقق من المجال والفرع الرئيسي والتحقق من residual،
  والمقاييس الكبيرة/الصغيرة، وعدم مساواة هوية عكسية وحدها بمرجع مستقل.
- للـiterative solvers: relative + absolute residual، حد iterations معلن،
  حالة الخروج، واختبارات stagnation؛ قيّم preconditioning في API مستقل.
- للهندسة المركبة والمتجهات: scaling وsigned zero وbranch cuts والقيم القريبة
  من overflow/underflow، واختبارات ملكية المصفوفات وعدم تعديل المدخلات.

### القبول

تحقق البواقي المتفق عليها على فئات المصفوفات المحددة، ورفض واضح عند فشل
المجال أو التقارب، مع تمييز ما لا يمكن استرجاعه بسبب سوء التكييف.

## المرحلة 5 — الدوال الخاصة

- أنشئ خريطة مجال لكل دالة: حول الصفر، المجال المتوسط، الذيل، وأماكن poles
  أو الفروع. اذكر الخوارزمية والمرجع وحد الانتقال في كل جزء.
- قارن series وcontinued fractions وrational/Chebyshev/asymptotic approximations
  حيث تلزم. لا تستبدل كل الطرق الحالية بطريقة واحدة عامة.
- قيّم خوارزميات معيارية موثقة لـBessel/Airy بدل الاعتماد طويلًا على quadrature
  مكلف لجميع المجالات؛ افحص حقوق استخدام أي coefficients أو تنفيذ منقول.
- وفّر scaled functions مثل الشكل الأسي المخفف حيث تمنع overflow/underflow
  مع بقاء المعلومة الرياضية مفيدة؛ تكون أسماء وعقود جديدة واضحة.
- اختبر الحدود من جهتين والـrecurrences/reflection identities والتداخل بين
  طريقتين، مع مرجع عالي الدقة مستقل عن تلك الهويات.

### القبول

لكل مجال مدعوم ميزانية خطأ مثبتة بالقياس، وانتقالات لا تخلق discontinuity
غير رياضية، وعدم إرجاع truncation غير متقارب بوصفه جوابًا ناجحًا.

## المرحلة 6 — التفاضل والتكامل والمعادلات والتحسين

- اشتق خططًا لفصل roundoff عن truncation في finite differences، مع إمكانية
  ضبط step وتقدير الخطأ دون كسر التواقيع القائمة.
- نفّذ دراسات تقارب عند تقليل step، وmanufactured solutions للتكامل وODE وPDE.
- اختبر التكامل على دوال حادة ومتذبذبة وقريبة من singularity، وعرّف المجالات
  التي تحتاج معالجة خاصة أو تقسيمًا من المستخدم.
- تحقق من معنى `Estimate.error`: تقدير محلي/مجموع تقديرات وليس ضمانًا صارمًا.
  عند الوصول إلى work budget يجب أن يُفصل عدم التقارب عن جواب موثوق.
- للـODE: forward/backward spans، أنظمة متعددة المقاييس، stiffness، الحفاظ على
  الكميات الفيزيائية المناسبة، event location، وتراكم الخطأ خلال خطوات كثيرة.
- للـoptimization: تعريف optimum محلي/عالمي وشروط unimodality أو convexity،
  والتحقق من constraints وKKT أو residual مناسب بدل مقارنة objective فقط.
- قيّم phase-I للـlinear programming كميزة منفصلة، مع infeasible/unbounded
  وdegeneracy/cycling؛ لا تدّعِ دعم القيود العامة في solver البداية الممكنة الحالي.

### القبول

دراسات تقارب تحقق الرتبة المتوقعة على المسائل المرجعية، ودقة ومقابلها تكلفة
مقاسان، وخروج واضح عند فشل الشروط أو التقارب.

## المرحلة 7 — الصيانة والأداء

### التنظيم

- قيّم تقسيم `math.quds` إلى وحدات داخلية حسب العائلة مع واجهة `quds:math`
  ثابتة. تحقق أولًا من loader والمسارات والخصوصية والتغليف؛ لا تختلق URIs
  جديدة لا يستطيع compiler أو النسخة المنشورة تحميلها.
- اجعل مصدر SDK المرجعي واحدًا، وتوليد النسخة المضمنة خطوة حتمية مفحوصة في CI.
- اختبر الاستعمال من checkout ومن حزمة منشورة/مفعّلة وفي مشروع آخر، لا من
  جذر المستودع فقط؛ يشمل ذلك show/hide/prefix وgo-to-definition.

### القياس والتحسين

- افصل زمن lexer/parser/analysis/codegen عن زمن kernel العددي.
- قس allocations ونسخ المصفوفات، خصوصًا `_put` و`_setColumn` داخل الحلقات.
- استخدم buffers محلية عند ثبوت عدم aliasing مع المدخلات، دون تغيير دلالات
  اللغة أو تجميد/نسخ كائنات المستخدم صامتًا.
- أنشئ benchmarks ذات warm-up وأحجام متعددة وmedian وتشتت، وسجّل الجهاز
  والإصدارات. حدد ميزانية الانحدار بعد القياس، لا من ضجيج تشغيل واحد.
- أضف قياسات VM وJS للدوال الحساسة؛ لا تفترض أن تحسين منصة يحسن الأخرى.

### القبول

تحسين مقاس دون تغير الدقة أو الملكية أو الـAPI، وتوليد SDK byte-identical،
وعمل الاستيراد من مشروع مستقل على المنصات المعلنة.

## المرحلة 8 — CI والإصدارات والتوثيق

- لكل PR: format/analyze، conformance وregressions، المرجع المجمد، اختبارات
  Quds، وتزامن المصدر/embedded SDK، وVM وJS smoke.
- تشغيل دوري أبطأ: شبكات أوسع عالية الدقة، fuzzing ببذور مسجلة، statistical
  sampling، وتحليل أداء. احفظ المخرجات المخفقة كحالات انحدار صغيرة.
- عرّف مصفوفة Dart المدعومة فعلًا؛ لا يكفي نص pubspec إن كانت الاعتماديات
  المقفلة أو اللغة تتطلب إصدارًا أحدث. افحص platforms التي سيُعلن دعمها.
- وثّق القيود، والتغييرات في الأخطاء والعتبات، والأمثلة وحدود الدقة لكل إصدار.
- لا تُرفع حالة API إلى مستقرة حتى يراجع شخص آخر العقد والأدلة. طلب مراجعة
  مستقلة للإصدار جزء من هذه الخطة، وليس تفويضًا تلقائيًا للنشر.

## حزم العمل الأولى المقترحة

1. **سجل العقود**: مخطط السجل + عقود integers/fractions كاملة + بقية APIs
   مصنفة بفجواتها، دون تغيير الخوارزميات.
2. **تقوية اختبارات الرفض والحدود**: أسباب أخطاء دقيقة، وفواصل خوارزميات
   Poisson/Bessel وغيرها، وحالات NaN/Infinity/±0 وفق العقود.
3. **ذيول التوزيعات**: شبكة عالية الدقة لـCDF/SF/log-probability، وتحديد API
   إضافي عند الحاجة، دون ترقيع النتائج بقصها إلى [0,1].
4. **الجبر الخطي**: بواقي المتجهات الذاتية وهويات pseudoinverse والتكييف، ثم
   إصلاح ما تكشفه هذه الاختبارات في PR منفصل.
5. **خريطة الدوال الخاصة**: مجالات ومراجع وbenchmarks، ثم تحسين عائلة واحدة
   في كل مرة مع مقارنة قبل/بعد.
6. **تنظيم الـSDK والأداء**: يبدأ بعد استقرار العقود كي لا يجمع refactor
   واسعًا مع تغيير عددي يصعب تشخيصه.

كل حزمة تخرج بكود/وثيقة محددة واختبارات ومعيار قبول. هذه حزم مقترحة، وليست
Issues منشأة على GitHub أو التزامًا بمواعيد أو تنفيذًا آليًا لها.
